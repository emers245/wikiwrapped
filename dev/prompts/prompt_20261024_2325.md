This prompt turns that into downloadable installers that non-technical users can run, built for free.

**Before planning, read what was actually implemented.** That means the path/resource resolution module, the launcher, `environment.yml`, `localconfig`, the Help content and the README. Don't assume they match the summary above. If anything this prompt relies on is missing or different (the resource-location hook especially), say so in your plan.

## Decisions already made (do not reopen)

1. **Full bundled Python via conda `constructor`, using conda-forge only.** No PyInstaller or Briefcase, no pip-only installs unless a dependency truly exists nowhere else (ask me first).
2. **Targets:** macOS arm64, macOS x86_64 (Intel) and Windows x64. Linux is not targeted.
3. **The installers are free and unsigned for v1.** On macOS, users approve the app once through System Settings → Privacy & Security → "Open Anyway". On Windows, they get SmartScreen's "More info → Run anyway". Code signing, notarization and SignPath are out of scope, but don't do anything that would make adding SignPath later hard.
4. **The UMAP reference space ships prebuilt inside the installer.** Users never build it. It's hosted as a GitHub Release asset, never committed to git.
5. **MiniLM (`sentence-transformers/all-MiniLM-L6-v2`) ships inside the installer, pinned to a specific HuggingFace revision.** The installed app must never contact HuggingFace.
6. **Install per user, with no admin rights, and keep user data out of the install directory.** Uninstalling or upgrading the app never touches the user's data.
7. **GitHub Releases host the installers.** GitHub Actions builds them.

### Milestone 1: Runtime environment and per-platform lock files

- **Audit what the installed app actually imports.** Cover the launcher, `app/`, `extract/` and `config.py`, and leave out tests and scripts. From that, produce a runtime spec separate from the dev `environment.yml`. The dev env should be the runtime spec plus dev tools, and it must not drift from the runtime spec: either the dev spec builds on the runtime one, or a check fails if they diverge. Report any current dependency the app doesn't need at runtime (pytest, httpx, matplotlib, and possibly pandas or pyarrow), with evidence.
- **Keep the fragile pins exactly as they are:** Python 3.11, numpy 1.26.4, numba 0.60.0, llvmlite 0.43.0, umap-learn 0.5.7, scikit-learn 1.5, pytorch 2.10.0. The reference-space pickle depends on them.
- **Force CPU-only pytorch builds on every platform.** A CUDA variant would add gigabytes.
- **Solve the runtime spec for osx-64, osx-arm64 and win-64, and produce explicit lock files** (for example with conda-lock, or explicit specs constructor can consume). If pytorch 2.10.0 CPU, or any other pin, doesn't resolve on one platform, **stop and present the options.** Don't relax a pin on your own.
- Report the estimated download and installed size per platform, along with the largest packages.

### Milestone 2: Bundled resources (reference space and model)

- **Model.** Write `scripts/fetch_model.py`, which downloads the MiniLM files at a pinned revision into a resources folder in the layout the app's resource resolver expects. Then:
  - Make `embeddings.py` load from that local path when present.
  - Set the HuggingFace and transformers offline environment variables in installed mode, so a missing file fails loudly rather than downloading.
  - Keep a dev fallback.
- **Reference space.** Work out which artifacts the app needs at runtime; for example, whether `reference_embeddings.npy` is needed or only the reducer and points. Then add a packaging script that:
  - bundles exactly those into one versioned archive, e.g. `reference-space-v1.tar.gz`
  - writes a manifest with sha256 checksums, the article count, and the exact versions of Python, numpy, numba, umap-learn and scikit-learn plus the MiniLM revision it was built with
  - gives the `gh` commands to upload it to a dedicated release, e.g. tag `reference-v1`. **I'll run the upload myself.**
- **Build-time fetch.** Write a script that downloads that asset, verifies the checksums, and refuses to proceed if the manifest versions don't match the runtime lock.
- **I'll build the full-scale reference space myself on my Mac.** It takes hours and hits Wikipedia's APIs. Don't run that build. Tell me the exact command and what to check afterwards. For developing and testing this milestone, use the existing small test build.
- **Consistency check.** Add a test, or a self-test step, that embeds a small fixed set of articles in the runtime env and checks the vectors against stored reference embeddings within a stated tolerance, such as cosine similarity > 0.999. Confirm that the reducer pickle loads and `transform()` runs. This is what catches cross-platform numerical or version drift.

### Milestone 3: Constructor installer, built and tested locally on my Intel Mac

- **Write the constructor config(s):** `.pkg` on macOS and the NSIS `.exe` on Windows. Default to a per-user install location, with no admin prompt where the format allows it, and explain any platform limits. The installers include the locked runtime env, the app code, the model and the reference space.
- **Choose how the app's own code gets into the installer.** Options include building it as a local conda package (which would need packaging metadata such as `pyproject.toml`) or copying it in with constructor's `extra_files` / post-install. Pick the simplest option that keeps the app code versioned and the resources read-only, and justify the choice.
- **Shortcuts via conda's `menuinst`:**
  - **macOS:** an app bundle in Applications, which the user can put in the Dock.
  - **Windows:** a Start Menu entry and a desktop shortcut that launch with `pythonw`, so **no console window appears**.
  - Make sure the app shows a proper name and icon in the Dock and taskbar.
  - Generate a simple placeholder icon in `.icns` and `.ico` from a single source image I can replace later, and document how to regenerate them.
- **Add a `--self-test` mode to the launcher.** It runs headless and exits 0 or 1 after checking:
  - the imports
  - that the model loads from the bundled path with no network access
  - that the reducer loads
  - that embedding and projecting a few titles works
  - the resource checksums
  - that nothing is written inside the install directory
- **Plan for upgrades and uninstalling.** Installing a newer version over an older one must work, and user data must survive it. On Windows that means constructor's uninstaller. The macOS `.pkg` has no uninstaller, so provide a documented uninstall procedure, or a small script, that removes the app but not the user data, and document separately how to remove the user data too.
- **Build the macOS x86_64 installer locally**, then install it into a clean location and run `--self-test`. Give me a manual checklist for testing it as a real user would: double-click the `.pkg`, approve "Open Anyway", launch from Applications, go through first-run setup, close and relaunch, upgrade, uninstall.

### Milestone 4: GitHub Actions builds for all three platforms
